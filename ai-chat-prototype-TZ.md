# Техническое задание: прототип ИИ-чата (ai-chat-prototype)

## 0. Контекст и цель

Нужно реализовать прототип веб-чата с LLM, состоящий из двух частей в одном git-репозитории:

1. **client** — фронтенд на Vue 3 + TypeScript + `ai-sdk` (Vercel AI SDK).
2. **server** — Node.js-сервер, который проксирует запросы в локальную OpenAI-совместимую LLM, хранит историю сообщений и управляет генерацией (включая стриминг, отмену и восстановление сессии).

Репозиторий `ai-chat-prototype` пользователь создаст и закоммитит в GitHub самостоятельно — Claude Code должен просто подготовить код проекта в рабочей директории (`~/tilda/ai-chat-prototype` или указанной пользователем).

Это **прототип**, не production-система: допустимы упрощения (нет авторизации/мультипользовательности, один "пользователь" на инстанс), но реализация должна быть рабочей и её должно быть легко проверить руками (`npm run dev` на клиенте и сервере).

## 2. Технологический стек

### Client
- Vue 3 (Composition API, `<script setup>`)
- TypeScript
- Vite как сборщик
- `ai` + `@ai-sdk/vue` (Vercel AI SDK) для работы с чатом и UI message parts (text, reasoning, tool-call/tool-result, error, source и т.д.)
- Минимальная стилизация (обычный CSS/SCSS, без UI-фреймворков — это прототип, важна функциональность, не дизайн)
- State management: Pinia не обязателен, можно обойтись composables, если это упростит код — на усмотрение реализации, но структура должна быть чистой и расширяемой

### Server
- Node.js + TypeScript
- Express (или Fastify — на усмотрение реализации, зафиксировать выбор в README)
- `ai` (Vercel AI SDK core) + `@ai-sdk/openai` (или `@ai-sdk/openai-compatible`) для обращения к LLM через OpenAI-совместимый API
- SQLite для хранения истории чатов и сообщений (`better-sqlite3` — синхронный, простой в использовании для прототипа)
- SSE (Server-Sent Events) для стриминга ответов LLM клиенту

## 3. Переменные окружения

Сервер настраивается через `.env` (в репозитории должен быть `.env.example`):

```
# Подключение к OpenAI-совместимой LLM
LLM_BASE_URL=http://localhost:PORT/v1
LLM_API_KEY=sk-xxxx
LLM_MODEL_ID=some-model-id

# Настройки сервера
PORT=3001
DB_PATH=./data/chat.sqlite
```

Клиент через `.env` (Vite `VITE_*`) должен знать URL сервера:

```
VITE_SERVER_URL=http://localhost:3001
```

## 4. Модель данных (SQLite)

Минимальная схема (можно расширять при необходимости):

**chats**
- `id` (text, PK, uuid)
- `created_at`
- `updated_at`

**messages**
- `id` (text, PK, uuid)
- `chat_id` (FK → chats.id)
- `role` (`user` | `assistant` | `system`)
- `parts` (json — массив UI message parts: text, reasoning, tool-call, tool-result, error и т.д., в формате, совместимом с ai-sdk `UIMessage.parts`)
- `status` (`complete` | `streaming` | `aborted` | `error`) — нужно, чтобы понимать, что сообщение ассистента ещё генерируется
- `created_at`
- `order` / `sequence` (для сохранения порядка сообщений в чате)

**generation_state** (для отслеживания активной генерации и возможности resume/cancel)
- `chat_id` (PK)
- `message_id` (id генерируемого сообщения ассистента)
- `accumulated_chunks` (json — накопленные части ответа на данный момент, для resume)
- `is_active` (bool)
- `abort_requested` (bool)

Точный DDL и способ сериализации оставить на усмотрение реализации, но описанные сущности и их назначение должны быть покрыты.

## 5. API сервера

Базовый префикс, например `/api`. Все эндпоинты работают с телом JSON, кроме генерации, которая отдаёт SSE.

### 5.1 `GET /api/chats/:chatId/messages`
Возвращает всю историю сообщений чата (массив `messages`, отсортированный по порядку). Если чата ещё нет в БД — создать пустой чат с этим id (или вернуть пустой массив, а чат создать при первом сообщении — определиться в реализации и задокументировать).

### 5.2 `POST /api/chats/:chatId/messages` — генерация ответа
Тело запроса — **только последнее сообщение пользователя** (клиент не пересылает всю историю):
```json
{ "message": { "role": "user", "parts": [{ "type": "text", "text": "..." }] } }
```
Сервер:
1. Достаёт из БД всю предыдущую историю сообщений этого чата.
2. Сохраняет присланное сообщение пользователя в БД.
3. Формирует полный список сообщений (история + новое) и отправляет в LLM.
4. Создаёт запись в `generation_state` (is_active=true) и новое сообщение-ассистента со status=`streaming`.
5. Стримит ответ клиенту через SSE, попутно сохраняя чанки в БД/`generation_state` по мере получения (чтобы был возможен resume).
6. По завершении — помечает сообщение как `complete`, снимает `is_active`.

### 5.3 `POST /api/chats/:chatId/messages/:messageId/regenerate` — перегенерация
Вместо тела с сообщением принимает **id существующего сообщения** (ассистента, которое нужно перегенерировать, либо сообщения пользователя, после которого нужно перегенерировать ответ — уточнить и зафиксировать выбранную семантику в README, рекомендуется: `messageId` — это id сообщения ассистента, которое нужно перегенерировать; сервер берёт все сообщения истории **до** него (не включая), отправляет их в LLM и создаёт новое сообщение ассистента взамен старого, либо обновляет то же самое — на усмотрение реализации, но должно быть однозначно и предсказуемо для фронта).
Использует тот же механизм стриминга/сохранения/resume, что и генерация.

### 5.4 `DELETE /api/chats/:chatId/messages/:messageId` — удаление сообщения
Удаляет сообщение из истории чата в БД. Отвечает 200/204. После успешного ответа клиент удаляет сообщение локально из списка.

### 5.5 `POST /api/chats/:chatId/cancel` — отмена генерации
Останавливает текущую генерацию для чата (если она активна): выставляет `abort_requested`, прерывает запрос к LLM, помечает текущее сообщение ассистента как `status=aborted` (сохранив то, что успело нагенерироваться), закрывает SSE-соединение с сервера.

### 5.6 `GET /api/chats/:chatId/resume` (SSE) — продолжение сессии
Вызывается при инициализации чата на клиенте (например, при обновлении страницы). Поведение:
- Если для этого `chatId` есть активная генерация (`generation_state.is_active === true`) — сервер сразу отдаёт клиенту уже накопленные чанки сообщения (из `accumulated_chunks`) и продолжает стримить новые чанки по мере их появления через тот же SSE-поток (клиент "досоединяется" к уже идущей генерации).
- Если активной генерации нет — эндпоинт может просто ничего не стримить / вернуть сигнал, что активной генерации нет (закрыть поток сразу).

> Примечание: п. 5.1 (список сообщений) и восстановление сессии (5.6) — два разных запроса при инициализации чата на клиенте, как описано в требованиях (см. раздел 7.5).

### Формат SSE-событий
Использовать протокол потоковых сообщений, совместимый с UI message parts из `ai-sdk` (text-delta, reasoning-delta, tool-call, tool-input-delta, tool-result, error, finish, и т.д.), чтобы на клиенте можно было напрямую использовать примитивы `ai-sdk` для парсинга потока и рендеринга частей сообщения. Точный набор типов событий — по возможностям используемой версии `ai-sdk` (data stream protocol / UI message stream), задокументировать выбранный формат в README сервера.

## 6. Инструменты (tools) на сервере

Реализовать пример серверного tool'а (передаётся в LLM как доступный инструмент через `ai-sdk` `tool()`), например: `getCurrentTime` — возвращает текущее время сервера, либо `calculate` — простой калькулятор выражения. Инструмент должен быть зарегистрирован в вызове генерации (`streamText`/аналог) так, чтобы LLM могла его вызвать, а результат tool-call/tool-result попадал в поток и сохранялся в истории сообщения как часть (`part`) с типом tool-call/tool-result.

## 7. Frontend — функциональные требования

### 7.1 Инициализация чата
При маунте компонента чата:
1. Сгенерировать/восстановить `chatId`:
   - Если в `localStorage` (или в URL) уже есть сохранённый `chatId` для текущей сессии — использовать его.
   - Если нет — сгенерировать новый (uuid) и сохранить.
2. Запросить с сервера историю сообщений: `GET /api/chats/:chatId/messages` и отрендерить их.
3. Запросить продолжение сессии: подключиться к `GET /api/chats/:chatId/resume` (SSE). Если сервер начинает присылать чанки — значит, была активная генерация, нужно "доотрисовать" сообщение в стриминговом режиме (как будто оно только что генерируется).

### 7.2 Отправка сообщения
Пользователь вводит текст, клиент отправляет **только это новое сообщение** на `POST /api/chats/:chatId/messages` и открывает поток SSE-ответа, отображая по мере получения:
- текстовые дельты (обычный текст ответа)
- reasoning (если LLM возвращает "размышления" — отображать визуально отдельно от основного текста, например, в свёрнутом/отличающемся блоке)
- tool-call / tool-result (отображать, что и с какими аргументами вызывался инструмент и что он вернул)
- ошибки (если LLM/сервер вернули ошибку — показать сообщение об ошибке прямо в чате как отдельный блок/сообщение)

### 7.3 Действия над сообщениями
У каждого сообщения (или как минимум у сообщений ассистента и пользователя — уточнить по смыслу, но реализовать логично для обоих, где применимо) должны быть кнопки:
- **Копировать** — копирует текстовое содержимое сообщения в буфer обмена (Clipboard API), без запроса на сервер.
- **Удалить** — отправляет `DELETE /api/chats/:chatId/messages/:messageId`; при успехе сообщение убирается из списка на клиенте.
- **Перегенерировать** — отправляет запрос на `POST /api/chats/:chatId/messages/:messageId/regenerate`, открывает SSE-поток и заменяет/дополняет сообщение новым сгенерированным содержимым по мере стриминга.

### 7.4 Кнопка "Стоп"
Видна только во время активной генерации (стриминга ответа). При нажатии:
1. Клиент делает `abort()` текущего fetch/SSE-запроса на клиенте (через `AbortController`).
2. Одновременно отправляет на сервер `POST /api/chats/:chatId/cancel`, чтобы сервер остановил генерацию у LLM (а не просто перестал слать данные клиенту, который уже отключился).

### 7.5 Кнопка "Новый чат"
Имитирует создание нового чата:
- Локально очищает список сообщений в интерфейсе.
- Генерирует новый `chatId` (uuid) и сохраняет его как текущий (в `localStorage`/состоянии).
- Дальнейшие сообщения отправляются уже с новым `chatId`. (Явный запрос на создание чата на сервере не обязателен — чат в БД создаётся implicitly при первом сообщении или при первом запросе истории.)

### 7.6 Пример клиентского tool'а
Реализовать пример **клиентского** инструмента (в отличие от серверного из раздела 6) через возможности `ai-sdk` для client-side tools — например, `logToConsole`, который просто делает `console.log(...)` с переданными LLM аргументами и возвращает подтверждение. Показать, как LLM может вызвать именно клиентский тул (а не серверный), и как результат его работы возвращается обратно в диалог/модель.

## 8. Обработка ошибок и edge cases

- Разрыв сети/сервера во время стриминга — сообщение должно корректно завершиться с пометкой ошибки, без "зависания" в состоянии "печатает...".
- Повторные подключения к `resume` при отсутствии активной генерации не должны ломать интерфейс.
- Удаление несуществующего сообщения / генерация для несуществующего чата — сервер должен возвращать осмысленные HTTP-ошибки (4xx) с телом, которое клиент может показать пользователю.
- Кнопка "Стоп" должна корректно работать даже если ответ уже почти полностью сгенерирован (не должно быть гонок состояний, ведущих к дублированию сообщений).

- Не требуется покрытие тестами, CI, деплой — только рабочий прототип, который можно запустить локально.
